# Patent Writing

## Purpose
- 将零散的技术想法整理为可提交给专利工程师或代理人的结构化材料。
- 默认采用中国发明专利中文表达习惯，必要时再调整为其他法域风格。
- 产出专利交底书、权利要求书初稿、背景技术、发明内容、实施方式、附图说明与审稿清单。
- 在写作前中后持续检查技术方案是否明确、是否有区别点、是否具备可扩展的保护范围。

## When to Use
- 你已经有一个技术方案，但表达分散，需要整理成专利交底书。
- 你需要把研发方案转成权利要求书初稿。
- 你需要评审一份专利草稿，识别保护范围过窄、技术效果不足、实施例不全等问题。
- 你需要把软件、系统、流程、算法、平台、交互、硬件、设备或工程方案改写为更适合专利表达的结构。

## Inputs
优先收集以下信息，缺失时先追问，不要直接硬写：
- 发明名称或临时标题
- 要解决的技术问题
- 现有方案为何不够好
- 核心技术方案与关键步骤
- 至少一个可落地实施例
- 与现有方案相比的区别点
- 预期技术效果
- 可替换实现、变体、边界条件
- 是否已有原型、代码、流程图、接口图、架构图、实验结果

## Outputs
可按用户要求输出一种或多种：
- 专利交底书
- 三段式技术交底书
- 权利要求书初稿
- 说明书摘要
- 背景技术与现有问题分析
- 发明内容与技术效果
- 实施例与附图说明
- 审稿清单与修改建议

固定模板资源：
- 技术交底书固定模板：[technical-disclosure-template.md](./assets/technical-disclosure-template.md)

## Workflow

### 1. 定义目标产物
先确认本次任务的目标是以下哪一类：
- 交底书优先：适合技术方案尚在整理阶段。
- 权利要求书优先：适合方案较成熟、区别点较明确时。
- 审稿优先：适合已有草稿，需要查漏补缺。
- 全套初稿：适合从零到一整理完整材料。

如果用户一次要求多个产物，按以下顺序处理：
1. 提炼发明点
2. 明确区别点与技术效果
3. 写交底书
4. 写独立权利要求
5. 展开从属权利要求
6. 补摘要、附图说明、审稿清单

### 2. 识别发明类型
判断方案更接近哪一类，并据此调整表达方式：
- 软件/算法类：强调数据对象、处理步骤、触发条件、输出结果、系统协同。
- 系统/平台类：强调模块、组件、通信关系、输入输出、控制逻辑。
- 流程/业务执行类：避免纯业务规则描述，尽量落到技术载体、数据流、系统动作、性能收益。
- 终端/设备类：强调硬件单元、传感、控制、存储、执行链路。

默认写作口径：
- 以中国发明专利常见章节结构组织说明书。
- 优先使用“技术问题 - 技术方案 - 有益效果”闭环表达。
- 术语表述偏中文专利文件风格，减少口语化和商业宣传语言。

如果方案看起来像抽象规则、管理方法或单纯人工决策：
- 先要求补充技术载体。
- 追问数据结构、系统处理逻辑、设备约束、性能指标或自动化实现。
- 若补不出技术实现，明确提示可专利性风险较高。

### 3. 提炼最小发明点
在正式写作前，必须先压缩为一段“最小发明点”表述：
- 现有技术中，什么场景存在什么缺陷。
- 本方案通过哪些关键技术特征解决该问题。
- 结果上带来什么技术效果。

推荐句式：
- 针对 A 场景下 B 问题，提出一种基于 C 的 D 方法/系统，通过 E、F、G 关键步骤，实现 H 效果。

如果最小发明点说不清：
- 暂停成稿。
- 回到输入阶段继续追问核心区别点。

### 4. 收集区别点与可保护层级
至少整理三层保护思路：
- 核心层：没有它方案就不成立的关键技术特征。
- 增强层：提高性能、准确率、稳定性、兼容性的附加特征。
- 变体层：替代实现、可选步骤、不同部署方式、不同参数范围。

写作时要避免两种常见错误：
- 只写结果，不写技术手段。
- 只写一个实施方式，导致保护范围过窄。

### 5. 生成专利交底书
如果用户未指定模板，技术交底书默认采用以下三段式结构：
1. 背景
2. 发明要点
3. 描述

优先按固定模板 [technical-disclosure-template.md](./assets/technical-disclosure-template.md) 组织输出；
如果用户已经指定章节标题或公司内部模板，再在保留该模板核心检查项的前提下调整格式。

三段式技术交底书默认内容要求：

1. 背景
- 说明本方案要解决的技术问题。
- 描述针对该问题的现有解决方案；如果用户要求或上下文允许，应补充检索到的对比文件或现有技术线索。
- 对每个对比文件或现有方案，说明其关键技术点。
- 分析现有方案的缺点、局限、成本、性能瓶颈、适用范围限制或实现复杂度。
- 明确为什么仍需要新的解决方案。

2. 发明要点
- 用较高抽象层级概括本方案的核心技术要点，先不陷入实现细节。
- 说明本方案相对现有方案新增了哪些关键区别特征。
- 说明采用本方案替代现有方案后获得的优势，优势必须与技术特征一一对应。

3. 描述
- 使用适当的文字、框图、流程图、模块关系图或时序说明来解释方案如何工作。
- 交代该方案要如何实施，包括输入、处理过程、关键判断、输出、模块分工、部署位置或设备关系。
- 说明至少一个可实施主例，以及必要时的替代实现。
- 如果适合，可补充建议绘制的图：系统框图、业务流程图、算法流程图、时序图、部署图。

如果用户明确要求更接近专利说明书体例，再扩展为以下补充章节：
1. 发明名称
2. 技术领域
3. 背景技术
4. 发明内容
5. 附图说明
6. 具体实施方式

交底书写作原则：
- 背景技术只写到足以引出问题，不长篇堆砌行业背景。
- 如果提到对比文件，至少给出“文件名称或来源线索 + 关键点 + 与本方案差异”的简短分析。
- 技术方案按对象、条件、步骤、结果展开，避免宣传式表述。
- 有益效果必须对应前文技术特征，不能空泛写“效率更高”。
- 实施方式至少写一个主实施例和一个变体实施例。

### 6. 生成权利要求书初稿
按先独立、后从属的顺序起草。

独立权利要求必须覆盖：
- 技术主题：方法、系统、装置、介质、设备中的一种或多种。
- 必要技术特征：解决问题所必须的步骤或模块。
- 特征之间的逻辑关系。

从属权利要求用于展开：
- 子步骤
- 参数条件
- 模块连接关系
- 数据对象定义
- 异常处理
- 优化逻辑
- 备选实现

权利要求写作原则：
- 用“包括”“用于”“根据”“响应于”等中性法律表达。
- 避免“最好”“优选但唯一”这类把范围写死的措辞。
- 不把具体数值、品牌、项目名直接写进独立权利要求，除非它们是必要特征。
- 若用户给的是代码实现，先抽象为技术步骤，再决定哪些细节放入从属项。

### 7. 生成摘要与附图说明
摘要：
- 控制在一段话内。
- 写技术领域、核心方案、主要用途和技术效果。
- 不写商业价值、市场价值。

附图说明：
- 为每张图给出一句用途说明。
- 若没有图，建议至少补流程图、系统框图、时序图中的一种。

### 8. 审稿与风险检查
完成初稿后，逐项检查：
- 是否明确了技术问题，而不是只描述业务目标。
- 是否写清核心技术特征之间的关系。
- 是否能看出与现有方案的区别点。
- 是否为每个关键区别点提供了技术效果。
- 是否至少给出一个可实施主例和若干变体。
- 独立权利要求是否过窄或遗漏必要特征。
- 从属权利要求是否只是在重复独立项而没有增加层次。
- 是否存在纯功能性表述过多、缺少实现手段的问题。
- 是否把实现细节写得过死，导致绕开容易。
- 是否存在前后术语不一致。

## Branching Rules
- 如果用户只有一句想法：先输出问题清单，不直接写完整草稿。
- 如果用户有详细方案但没有区别点：先做“现有技术 vs 本发明”对比表。
- 如果用户要求写技术交底书：默认按“背景 / 发明要点 / 描述”三部分输出，除非用户明确要求改成别的模板。
- 如果用户要求列出对比文件：先说明是否已提供检索材料；若未提供，只能基于用户给出的现有方案或公开线索做比较，并明确标注哪些内容仍需检索验证。
- 如果用户提供的是代码或流程图：先抽象出技术特征，再写交底书或权利要求。
- 如果用户已经有草稿：优先做审稿清单和修改建议，再决定是否重写。
- 如果用户要求“写得宽一点”：扩大独立项抽象层级，同时把具体实现下沉到从属项和实施例。
- 如果用户要求“尽量能授权”：优先保证必要技术特征闭环、效果可论证、实施例充分，不盲目追求过宽。

## Completion Criteria
只有满足以下条件才算完成：
- 发明点可以用 1 到 3 句话清晰说明。
- 技术问题、技术手段、技术效果三者闭环。
- 至少有一个主实施例和一个替代实施例。
- 至少形成一条独立权利要求和若干从属权利要求的层级结构。
- 术语前后一致，没有明显宣传性或商业性语言。
- 用户能直接把结果拿去继续内部评审或交给专利代理人加工。

## Response Pattern
执行时优先采用以下输出顺序：
1. 发明点摘要
2. 缺失信息与关键追问
3. 交底书或权利要求书正文
4. 审稿风险提示
5. 下一步建议

当目标产物是“技术交底书”时，正文默认顺序为：
1. 背景
2. 发明要点
3. 描述

默认直接套用固定模板 [technical-disclosure-template.md](./assets/technical-disclosure-template.md)，
将缺失信息保留在“待补充信息”部分，不要为了填满模板而臆造事实。

其中“背景”部分优先包含：
- 技术问题
- 现有方案
- 对比文件或公开方案分析
- 现有方案缺点

其中“描述”部分优先包含：
- 文字说明
- 建议补充的框图/流程图
- 具体实施方式

如果输入不足，先只输出：
- 当前可确认的发明点
- 还缺哪些事实
- 需要用户补的最关键 3 到 7 个问题

- 根据下面的系统设计，生成权利要求书初稿，包含 1 条独立权利要求和 8 条从属权利要求。

- 把这段代码实现抽象成适合专利申请的技术方案。
- 将下面的软件流程整理为“背景技术 + 发明内容 + 具体实施方式”。

## Notes
- 这是写作与结构化整理技能，不替代正式法律意见。
- 涉及新颖性、创造性、授权概率时，应提示用户结合检索结果和代理人意见进一步判断。
